# 2026-11-24 检索延迟排查

排查对象为 `172.19.40.22:8424` 的现有 Knowledge 服务。本文只记录诊断，没有修改生产检索策略、门槛或重启服务。线上仍为代码 `cf09e3a` 的统一混合检索镜像。

## 结论与证据

主要耗时在每次查询实时调用 TokenHub 生成查询向量。增加的流量进一步增加排队风险；本地 BM25、正文读取和向量扫描不是当前主要耗时项。没有证据表明 TokenHub 相比此前变慢，当前测量证明的是调用链中的耗时占比。

采集北京时间 09:16:55–11:16:52 的两小时服务端日志：

| 接口 | 次数 | P50 | P95 | P99 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| search | 28,385 | 724ms | 1,555ms | 1,764ms | 5,028ms |
| page/read | 71,323 | 1ms | 3ms | 6ms | 33ms |
| get | 99,826 | 1ms | 2ms | 5ms | 38ms |

上述 search 均返回 HTTP 200；但当前 HTTP 日志不包含 `retrieval.mode/fallback_reason`，所以不能据此断言没有发生普通库 BM25 降级。两小时只见一次 page/write 和一次向量 ready 日志，不符合批量写入阻塞全库查询的表现。现有 6 库向量均 ready，采样时均未构建中。容器无重启、健康正常；主机负载采样约 3.5，Knowledge CPU 约 49%，内存约 5.7GiB。它们不是长期资源监控结论。

流量从 09:20–09:59 平均 **34.8 次检索/分钟**，增加到 10:15–11:15 平均 **382.3 次/分钟**，约 11 倍。对应的每分钟 P50 的中位数从 613ms 升到 757ms。部分分钟超过 450 次。流量明显增长，但不能把所有固定的向量调用成本都归因于流量增长。

## 只读探针

同一查询“账号交易”交替请求 BM25 和 hybrid：

| 库 | BM25 两次 | hybrid 两次 |
| --- | --- | --- |
| 正式审核 wiki-zz5wwtdt | 5 / 5ms | 652 / 801ms |
| 客服 wiki-xot2bcfn | 15 / 14ms | 1,176 / 527ms |

两个判例库各一次查询为 646ms、800ms，仍返回 strict hybrid 和 0.85 门槛。

另用相同生产 worker、模型配置和现有索引做 8 次串行只读查询，在独立诊断 worker 中包裹 fetch，记录请求前后时点，不修改服务进程：

- 完整 worker：591–735ms。
- 启动及加载模块到发起模型请求：40–44ms。
- TokenHub HTTP 请求到 JSON 完整解码：487–596ms。
- JSON 解码后到 worker 退出（包括本地扫描、排序、清理）：21–96ms。

模型调用约占这些探针总耗时的 80–90%。模型时段包含网络、TLS、上游排队/推理和响应解析，不能把它全部称为模型推理时间。

同一持久 Node 进程连续 6 次调用模型：471、461、392、341、372、297ms。说明连接和进程复用值得优化，但这些顺序样本不足以精确分离 TLS 和上游负载，不能将前后差额全归于 TLS。

## 代码对应

- `vector-client.ts` 每次查询新建一个 worker，结束后退出；普通和判例各 4 个并发槽位、最多 8 个排队，含排队预算 5 秒。
- `vector-worker.ts` 每次 search 都调用 `embed(query)`，然后扫描当前 Wiki 的向量。
- `vector-shared.ts` 的 embed 每次向 TokenHub `/embeddings/multimodal` 发请求。
- 文档向量已缓存；查询向量没有共享缓存或相同请求合并。因此调用方缓存未命中的每个请求都付出实时向量调用成本；一次查询跨多个库还会重复向量化相同文本。

现有日志没有每条查询的队列等待、Wiki、模型耗时及 fallback 字段。因此排队是由容量与流量支持的放大因素，尚未直接测得每个请求的排队时间，不能精确给出其占比。

## 后续优化顺序

1. 增加分阶段耗时与队列计数日志，不记录原始查询、Key；包含 Wiki、检索实际模式、fallback 原因。
2. 增加进程级、精确文本与模型配置隔离的查询向量短期缓存，以及同一查询并发合并。跨 Wiki 可复用查询向量，但页面召回、revision 核对、0.85 逐条过滤仍分别执行。缓存应有容量与 TTL 限制。
3. 持久 worker 池复用 HTTP 连接，并避免每次重新加载模块。上线前用同一查询集和并发流量验证结果及延迟。
4. 根据队列实测调整并发，保留普通/判例隔离；不直接无限扩大向量请求数。
