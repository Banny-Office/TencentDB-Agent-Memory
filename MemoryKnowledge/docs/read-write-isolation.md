# Wiki 写入与检索隔离

## 问题

`page/write` 过去在 HTTP 主线程写入页面后调用同步 `wikiMgr.sync`，扫描整个 Wiki、分词并重建 FTS5/元数据/图谱。即使写入的是另一个 Team 或 Wiki，也会阻塞同进程的生产检索。2026-11-12 线上 DKE 暂存库增长到 17,901 页，连续单批写入触发全库重建，日志记录约 6–7 秒一次。

## 实现和接口契约

- 运行时完整索引重建移到独立 Node worker thread。所有 Wiki 共享一个构建并发槽，最多等待 64 个构建任务；不为每个请求无限创建线程。
- 重建和读取共用原有分词、摘要、BM25 和图谱算法；不减少 Top K，不改写知识，不引入搜索缓存。
- 继续使用原有每 Wiki SQLite WAL 数据库，三张索引表在一个事务中提交。搜索的 FTS 和图谱读取也放在同一个读事务中，防止 worker 提交时读到混合版本。
- 同一 Wiki 的 REST 操作与工具查询通过同一个进程内队列协调。写入等待索引提交后才返回 200；同 Wiki 的查询等待写入完成，其他 Wiki 的查询不等待该队列。
- 索引重建失败返回 503，提示文件写入可能已经发生。该 Wiki 的正文和检索随后也返回 503，避免把新正文和旧索引作为有效知识。修复原因并成功重建后恢复；不能把未知结果当作未写入自动重试。
- 摄取的索引/源状态仍在同一个事务中提交；索引阶段也使用 worker。启动恢复仍按原逻辑同步执行，在监听 HTTP 前完成。
- 入口地址、请求格式、用户凭据和数据目录不变。普通单批文件操作仍有同步 I/O；worker 隔离不是独立磁盘或主机的资源隔离。

## 构建与验证

`npm test` 先构建 worker，再运行真实 SQLite、worker 与 Hono 回归测试；`npm run typecheck` 校验类型。源码开发模式也需要先运行 `npm run build`，以生成 `dist/index-worker.mjs`。发布时必须包含整个 `dist/`，不能只替换 `server.mjs`。

上线前在独立数据卷/仅回环端口的容器中完成：

1. 使用线上原有依赖构建，不随修复升级运行时依赖。
2. 对每个正式 Wiki 对比原服务与候选服务的查询结果、排序、分数、图谱及正文哈希。
3. 在暂存库副本连续批量写入，同时轮询正式 Wiki 副本的 get/search/page/read/health，统计端到端 P95、最大延迟和失败数。
4. 确认写入返回后新页面可检索、可读取；并发的同 Wiki 修改不能交叉覆盖构建。
5. 验证原服务的文件指纹在测试前后未变，所有写入测试只发生在副本。

## 发布及回滚

保留原容器、镜像和受保护配置。预建新容器，复用原环境变量、网络、端口和生产数据卷，并复制容器内非卷挂载的 Panel 配置。切换时仅停止并替换 Hub，不重启 Core、Proxy 或 Router。启动后验证健康、正式 Wiki 结果和正文哈希。

失败时停止新容器并恢复原容器。本修改没有数据格式或 schema 迁移，原索引算法和数据库格式兼容。回滚不能删除生产数据卷，也不能用测试数据卷替换生产数据。

## 限制

这不是多实例同时写同一数据目录的方案。不要让两个 Knowledge 服务同时挂载同一生产数据卷读写。批量测试或导入若要获得更强资源隔离，应使用独立服务、独立卷和 CPU/内存配额；仍共享主机时，磁盘 I/O 依然可能竞争。测试通过不等于已经完成全量审核精度评测。

## 2026-11-12 隔离副本实测

在原宿主机、相同原运行依赖、各限 1 CPU 的独立容器/数据卷中，对 17,901 页 DKE 暂存库副本连续写入 3 批，每批 20 页，同时以 2 秒请求超时轮询另一正式审核库的搜索、正文和健康接口：

| 项目 | 原实现 | worker 实现 |
|---|---:|---:|
| 每批写入耗时 | 6.88–7.59 秒 | 6.94–7.70 秒 |
| 查询/健康超时次数 | 27 | 0 |
| 成功查询/健康样本数 | 12 | 601 |
| worker 期间搜索 P95 / 最大值 | — | 13.73 / 81.67 ms |
| worker 期间正文 P95 / 最大值 | — | 9.37 / 61.88 ms |

写入本身仍执行完整重建，本修复消除了它占用 HTTP 事件循环造成的跨 Wiki 阻塞。上述延迟为宿主机回环端到端耗时，不代表任意客户端网络的延迟上限。

四个 Wiki 的 32 次 Top-8 搜索及命中正文对比共 62 项全部一致；6 项回归测试覆盖排名/图谱一致性、跨 Wiki 响应、同 Wiki 串行、索引失败关闭与恢复、索引/源状态事务回滚以及失败写入不得返回成功。没有调用审核模型或提交业务判罚，尚未进行全量审核精度评测。

复测脚本：`scripts/verify-index-isolation.py`。需要显式指定独立回环端口和 `--allow-write-to-copy` 才会执行写入；生成报告仅包含指纹、计数和延迟，不保存知识正文。所有压力写入仅发生在副本。

部署记录：2026-11-12 18:48（北京时间）已切换现有 8424/8125 服务。生产复核 62 项结果/正文指纹一致，28,186 个受保护文件指纹不变；Core/Proxy 保持原容器，Router 未修改。保留 `tdai-memory-hub-before-query-isolation-20261112` 作为回滚容器，配置及元数据备份保存在宿主机受保护的发布目录。验证容器使用独立数据卷，不会向生产卷回写测试数据。
